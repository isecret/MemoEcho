## 1. 文档目的

本文档将 [PRD.md](./PRD.md) 中已更新的产品需求拆分为可执行的 `Epics` 和 `Stories`，用于后续排期、任务分派和 issue 管理。

拆分原则：

- 以首版 `MVP` 为边界
- 优先保证主链路可用
- 每个 Story 必须具备明确交付结果
- 每个 Story 尽量可独立验收

## 3. Epic 详情

## E1. 应用骨架与菜单栏

### 目标

建立首版 macOS 菜单栏应用骨架，提供最基础的应用入口和状态展示能力。

### Stories

#### S1.1 初始化 macOS 应用工程

作为开发者，我需要一个基于 `Swift + SwiftUI + AppKit` 的项目骨架，以便后续实现菜单栏应用。

验收标准：

- 工程可在 Xcode 中打开并运行
- 应用启动后可正常驻留于菜单栏
- 项目目录结构清晰，至少包含 UI、Domain、Providers、Platform、Persistence 分层入口
- 客户端整体架构采用 `MVVM + Service Layer`

#### S1.2 实现菜单栏图标与菜单

作为用户，我希望应用在菜单栏中有基础入口，以便访问核心功能。

验收标准：

- 菜单栏图标可见
- 菜单中包含 `打开设置`、`退出应用`
- 处理中状态下菜单中出现 `取消当前任务`
- 注入失败时菜单中显示失败文本预览，可点击复制

#### S1.3 实现菜单栏品牌图标与 HUD 状态反馈

作为用户，我希望从菜单栏访问应用，并通过 HUD 了解录音与处理状态。

验收标准：

- 菜单栏使用固定的 UFO 模板图标，适配浅色与深色外观
- HUD 随主链路展示录音、处理、成功或失败反馈

依赖：

- 无

## E2. 设置页与本地配置

### 目标

提供首版必需的配置入口，并实现普通配置与密钥的本地持久化。

### Stories

#### S2.1 实现设置页基础框架

作为用户，我希望有一个统一的设置页配置应用，以便在首次引导后日常调整设置。

验收标准：

- 应用可从菜单打开设置页
- 首次启动由独立引导窗口负责准备，设置页保留日常配置入口
- 设置页包含 LLM、快捷键、权限、诊断模块占位

#### S2.3 实现 OpenAI 兼容 LLM 配置表单

作为用户，我希望填写 LLM 配置，以便应用可以完成文本润色。

验收标准：

- 支持输入 `Base URL`、`API Key`、`Model`
- 支持在 `Base URL` 和 `API Key` 完整时从 OpenAI 兼容 `/models` 获取候选模型
- 当服务不支持 `/models` 或获取失败时，仍可手动输入 `Model`
- 配置值可保存并重新加载

#### S2.4 实现功能开关与快捷键配置项

作为用户，我希望设置全局快捷键，以便稳定触发录音。

验收标准：

- 支持设置并展示全局快捷键
- 配置值可保存并重新加载

#### S2.5 实现配置存储策略

作为开发者，我需要区分普通设置和敏感密钥的存储位置，以保证安全性和可维护性。

验收标准：

- LLM API Key 存储到 `~/.memoecho/config.json`
- 普通设置存储到 `UserDefaults`
- 应用重启后可恢复配置
- 保存配置时做轻量格式校验，真正联网调用时再做严格失败

依赖：

- E1

## E3. 权限管理

### 目标

完成首版所需的麦克风权限与辅助功能权限引导和状态展示。

### Stories

#### S3.1 实现麦克风权限检测与引导

作为用户，我希望知道应用是否有录音权限，并能被引导去授权。

验收标准：

- 设置页可展示麦克风权限状态
- 权限缺失时提供明确引导
- 未授权时无法开始录音

#### S3.2 实现辅助功能权限检测与引导

作为用户，我希望知道应用是否有文本注入权限，并能被引导去授权。

验收标准：

- 设置页可展示辅助功能权限状态
- 权限缺失时提供明确引导
- 未授权时注入动作会失败并返回明确错误

#### S3.3 实现首次语音输入准备向导与运行前就绪检查（#123）

作为用户，我希望通过视觉演示完成语音识别、AI 模型、权限和快捷键准备，并在条件失效时快速恢复使用。

验收标准：

- 首次启动自动打开独立欢迎页；欢迎页不计数，正式步骤固定为 ASR → LLM → 权限 → 快捷键 → 试用
- 每页短标题、至多两行介绍和一个突出主操作；所有页面统一上方主视觉、下方标题说明的布局，标题区下移 24pt 并保持同一基线，导航位置不变；主视觉区域不少于页面高度 50%，最后一步保留紧凑输入框；使用原生 macOS、SF Symbols 和现有 HUD 元素
- 正式步骤左下角仅显示 `1 / 5` 至 `5 / 5`；支持 VoiceOver“第 N 步，共 5 步”、深浅色和“减少动态效果”
- 本地模型可在引导内下载、失败重试并跨步骤继续；云端 ASR 与 LLM 必须完成真实请求验证，模型列表失败仍可手动输入 Model
- 麦克风未决定、拒绝、受限分别提供正确操作；辅助功能授权单独展示，所有系统授权操作 single-flight
- 用户明确接受默认快捷键或录制新组合；以可读 keycap 展示左右修饰键，新值注册成功后才保存，失败恢复旧配置
- `OnboardingProgress` 保存展示进度，与动态 `VoiceInputReadiness` 分离。自动启动续接未完成进度，快捷键缺项恢复定位对应步骤；手动从菜单重开则从欢迎页开始，不重置已有配置或完成标记。已打开窗口保留当前步骤，不被重复入口打断
- 每次开始录音前检查快捷键、麦克风、辅助功能、ASR、LLM；任一项未就绪时不创建 session，定位第一个所需步骤
- 引导其它步骤、模型下载未完成、授权或验证中，重复快捷键不创建 session、不重复窗口或系统弹窗；就绪的前台试用页可直接按快捷键启动，无需先点击文本框
- 欢迎页不展示 Logo，副标题“多说话，少打字。”；聊天示例是朋友提问、用户用语音回答的双人对话，使用聊天输入框和工具栏，循环演示唤起语音 → Thinking → 完成填入；真实 HUD 组件保持实际尺寸，演示不录音、不联网、不自动发送，减少动态效果时展示静态填入结果
- 欢迎页使用用户提供的打包头像与产品灵感聊天文案；HUD 上移至输入框内部、工具栏上方，不与文字或边框重叠，各演示阶段布局不跳动。语音识别页移除主图标下方重复的语音转文字图标；AI 模型页以更热情、啰嗦的口语化产品设计 idea 展示明显但不扩写的整理对比
- 快捷键页以一组可编辑的大键帽为主视觉，增加按键底边、高光和轻阴影，不展示装饰性 HUD 或重复的小键帽
- 试用页提供可编辑文本框与示例文案，移除键帽和底部重复提示，保留错误及未就绪恢复入口。全部 ready 且本页前台时，快捷键显示实际 HUD 并显式触发真实 ASR 与 LLM 试用；结果仅回填本页，不读取配置窗口上下文或向其他应用注入。离页/关窗取消试用并丢弃迟到结果
- 试用页移除绿色完成图标，140pt 输入框置于上方主视觉区，示例放在框下；全部就绪时在共享标题区显示“设置完成”与一句可选试用说明。输入框、示例和必要反馈沿 550pt 内容宽度左对齐，导航固定底部。输入框无滚动条，长文本仍可滚动编辑；未就绪时不显示完成状态
- 进入就绪的第五页时自动聚焦输入框，包括关闭后重开；未就绪或离页时不抢焦点。空框提示“按下快捷键 {当前快捷键}，开始说话…”，左右修饰键及组合显示与设置页一致；聚焦不自动录音
- “开始使用”仅在必要项全部 ready 且无试用正在进行时可完成；试用非强制条件，任何配置完成事件都不自动录音
- 完成后权限撤销、模型丢失或配置失效时，直接定位对应恢复步骤
- 单元测试覆盖 readiness 组合与路由、进度恢复、single-flight、验证状态和快捷键注册回滚；真实 TCC、下载与辅助功能由手工验收覆盖

依赖：

- E1
- E2

## E4. 全局快捷键与录音

### 目标

打通录音能力，支持全局快捷键单按／双按切换，以及按住说话、松开提交。

### Stories

#### S4.1 实现全局快捷键注册

作为用户，我希望通过全局快捷键触发录音，而不必切换到应用窗口。

验收标准：

- 应用可注册单一全局快捷键
- 快捷键在常驻菜单栏状态下可生效
- 修改快捷键后立即生效
- 设置页以键帽展示组合，录制与展示分离；注册失败时不保存新值并恢复原快捷键

#### S4.2 实现按下切换录音模式

作为用户，我希望按一次快捷键开始录音、再按一次结束录音，以获得简洁直觉的交互。

验收标准：

- 按下快捷键开始录音
- 再次按下快捷键结束录音
- 处理中（`transcribing / polishing / injecting`）再次按键忽略
- 录音状态能反映到菜单栏

#### S4.6 实现短录音静默取消

作为用户，我希望误触或极短录音不会触发识别、润色和注入，避免产生奇怪文本或浪费处理资源。

验收标准：

- 录音时长低于 `500ms` 时静默取消
- 短录音不进入降噪、ASR、LLM 或文本注入
- 短录音不展示错误摘要
- 短录音不生成注入失败文本
- 诊断日志记录 `short_recording_cancelled`

#### S4.4 实现音频格式标准化

作为开发者，我需要统一录音输出格式，以便稳定提交给 ASR。

验收标准：

- 音频输出格式固定为 `PCM/WAV 16k mono`
- 主链路可复用标准化后的音频结果

#### S4.7 实现菜单栏麦克风选择

作为用户，我希望在菜单栏直接选择录音麦克风，以便在多个输入设备之间快速切换。

验收标准：

- 菜单栏一级菜单包含 `麦克风` 子菜单，不额外展示当前设备名称
- 子菜单包含 `自动选择（推荐）`、`系统默认($当前选择输入设备名)` 和当前所有可用麦克风；新配置默认自动选择，已有选择保持不变
- 自动选择在默认蓝牙输入与蓝牙输出并存时优先使用开盖、未静音且可用的内置输入；合盖、无可用内置输入或默认输入为有线/外置设备时保留系统默认输入。明确指定设备时不自动覆盖
- 设备列表及默认输入/输出变化通过系统事件刷新，录音开始前重新解析；不通过持续轮询或录音中打开候选麦克风来探测
- 提示音沿用 A「柔和双音」资源，时序对齐 Typeless：采集开始后按同设备 / AirPods 输出 / 其他设备分别延迟 1200 / 300 / 0ms；正常结束时先播放 End，100ms 后关闭采集。短录音不播放 End，停止或取消会取消待播 Start，不自动重播或发送静音保活
- 自动化验证覆盖三种输入选择及保存恢复、合盖和设备不可用回退、三档提示音延迟、取消待播 Start、End 与采集关闭顺序、重复停止、取消后旧回调不影响新会话；真实蓝牙设备下的音量、音质和路由切换仍需手工验收
- 当前选择用勾选展示
- 点击设备后立即保存配置，但仅影响下一次录音
- 录音、识别、润色、注入期间禁用麦克风切换
- 已选设备不可用时自动切换到系统默认输入，不额外展示不可用提示项
- 音频输出仍固定为 `PCM/WAV 16k mono`

#### S4.8 支持 Fn／🌐 键作为全局快捷键

作为用户，我希望将 MacBook 的 `Fn`／🌐 键设为全局录音快捷键，以便单指完成按一次开始、再按一次结束的录音操作。

验收标准：

- 设置页可录制并显示 `Fn / 🌐` 单键快捷键，保存后立即生效，重启后加载一致
- `Fn` 快捷键在 MemoEcho 前台及其他应用前台均可触发；按住不重复触发
- `Fn` 与修饰键的组合同样可录制和触发；按 F1–F12 等功能键不会误触发已绑定的 `Fn` 快捷键
- 现有普通组合键与左右侧纯修饰键快捷键行为不回归
- 含 `Fn` 的配置使用当前快捷键 JSON 结构持久化
- 选中 `Fn` 时设置页提示：若系统「按下 🌐 键时」配置了动作，需在系统设置中改为「无操作」

依赖：

- E1
- E2
- E3


#### S4.9 三种录音方式（Issue #8）

- 设置及引导共用单按／双按／按住，默认单按；录制新快捷键保留方式。
- 双按 400ms 窗口、完整释放、抗重复与组合键干扰；首按无反馈。
- 按住立即录音、松开提交，仅结束对应会话；组合键及监听中断取消，保留 Shift+Tab。
- 缺失 triggerMode 保留原行为及确认指纹；注册／保存失败回滚。处理中禁用编辑与触发。
- 自动回归及真实设备验收见 [方案](./plans/hotkey-recording-modes.md)。

## E6. OpenAI 兼容 LLM 集成

### 目标

接入用户自定义 OpenAI 兼容模型服务，实现固定边界的文本润色。

### Stories

#### S6.1 实现 OpenAI 兼容 LLM Provider

作为开发者，我需要一个标准化的 LLM 调用层，以便对接不同 OpenAI 兼容网关。

验收标准：

- 对齐 `OpenAI Chat Completions` 接口形态
- 支持 `Base URL`、`API Key`、`Model`
- 调用层独立于 UI
- 可返回统一的文本结果模型
- Provider 内部负责固定超时与取消控制

#### S6.2 实现固定润色 Prompt 策略

作为产品，我希望首版的 LLM 行为边界稳定可控。

验收标准：

- Prompt 明确限制为纠错、同音词/错别字修正、去赘词、轻度书面化、补中文标点
- Prompt 明确要求保留个人词典中的专有名词
- 不暴露用户自定义 Prompt 能力
- 不暴露高级模型参数

#### S6.3 基于 LLM 配置自动启用润色

作为用户，我希望只要 LLM 配置完整就自动启用润色，避免额外开关带来的歧义。

验收标准：

- 不再提供独立的 `启用 AI 润色` 开关
- `Base URL`、`API Key`、`Model` 三项完整时自动启用 LLM
- 三项全空或半填时允许保存，但运行时视为未配置完成

#### S6.4 实现 LLM 失败处理

作为用户，我希望 LLM 配置异常或请求失败时得到明确错误，而不是被自动注入未经润色的文本。

验收标准：

- LLM 配置不完整时直接报错，不执行注入

## E18. LLM 保守型结构化处理

### 目标

在保持 OpenAI Chat Completions 协议、固定 Prompt、默认自动处理和“不扩写、不改原意”原则不变的前提下，为 LLM 链路增加保守型结构化处理中间层，提升列表化表达、消息化表达和显式自我修正场景的稳定性。

### Stories

#### S18.1 定义结构化结果模型

作为开发者，我需要让 LLM 输出既能承载结构化结果，又尽量不破坏现有主链路。

验收标准：

- 新增内部枚举 `PolishMode`，至少包含 `plainText`、`list`
- 新增 `StructuredPolishResult`，可承载 `mode`、`intro`、`items`、`outro`、`correctionApplied`，并提供 `isValid` 语义校验
- `PolishResult` 保留现有 `text`，并包含必需的 `structured`
- `LLMProvider -> SessionCoordinator` 消费结构化结果及本地渲染后的 `text`

#### S18.2 升级固定 Prompt 支持 plain_text / list

作为用户，我希望 AI 在不扩写的前提下，能自动把明显的列表和短消息整理得更自然。

验收标准：

- Prompt 保持固定内置，不开放用户自定义
- `plain_text` 继续覆盖纠错、同音词、赘词、标点和轻度书面化
- `list` 可识别明显枚举信号并输出条目结构；若原话包含列表前言或列表后补充说明，应一并保留；信号不足时回退 `plain_text`
- 短消息口述、回复口述、转发口述统一保持 `plain_text`
- Prompt 明确支持“不是 A，是 B”“改成”“最后一句不要了”等显式自我修正
- 个人词典继续作为术语参考进入 Prompt，且不被视为可执行指令

#### S18.3 实现结构解析与本地渲染

作为系统，我需要优先消费结构化结果，，结构失败时直接报错。

验收标准：

- 客户端优先解析 LLM 返回的结构化 JSON
- 本地支持 `plain_text`、`list` 两类渲染
- 当结构字段与自由文本冲突时，以客户端本地渲染结果为准
- 非法 JSON、缺字段或文本提取失败时直接报错，不注入文本
- LLM 失败、超时、空响应时，仍直接报错且不注入任何文本

#### S18.4 补充结构化处理调试日志与诊断字段

作为开发者，我需要在 Debug 模式下判断本次结构化处理走了哪条路径，以便快速定位问题。

验收标准：

- Debug 日志记录本次 `mode`
- Debug 日志记录是否触发 `correctionApplied`
- 结构化解析失败记录为 LLM 响应格式错误
- Release 构建继续遵守脱敏约束，不输出 ASR 原文、LLM 正文或密钥

#### S18.5 补充测试覆盖并同步 PRD/TDD/EPICS 文档

作为团队，我需要为结构化处理中间层补齐测试和文档，确保实现与定义一致。

验收标准：

- 增加 `plain_text`、`list` 两类行为测试
- 增加“不是 A，是 B”“改成”“最后一句不要了”等自我修正测试
- 增加非法 JSON、缺字段直接失败测试
- 继续验证 LLM 失败时不注入文本
- `docs/PRD.md`、`docs/TDD.md`、`docs/EPICS_AND_STORIES.md` 同步反映结构化处理边界与实现拆分

## E19. 长录音分段 ASR

### 目标

通过音频静音分段，移除固定录音时长上限，支持长时间录音。AudioSegmenter 对录音流实时分析，按静音检测和 55s 强制上限切段，分段串行提交至现有 ASR 平台，拼接转写文本后交给 LLM 润色。

### Stories

#### S19.1 实现 AudioSegmenter 组件

作为系统，我需要一个音频分段器，能够实时分析 PCM 流并自动切段。

验收标准：

- `AudioSegmenter` 接收 PCM chunk 流（16kHz mono），实时分析音频能量
- 支持静音检测切段：连续静音 ≥1.6s 且已录 ≥15s 时切段
- 支持 55s 强制切段：单段达到 55s 时无条件切段
- 切段后保留 300ms 尾部静音避免截断语音
- 输出 `SealedSegment` 包含 `segmentIndex`、PCM 数据、时长、切段原因（静音/强制）
- 最终调用 `finalize()` 输出最后一段

#### S19.2 SessionCoordinator 分段 ASR 编排

作为系统，我需要 SessionCoordinator 管理分段 ASR 队列，实现录音与 ASR 并行。

验收标准：

- 录音期间，已 sealed 的分段立即提交降噪和 ASR，不等待录音结束
- 分段 ASR 严格串行执行，避免 sidecar/云服务并发问题
- 录音结束后识别最后一段
- 所有分段 ASR 完成后，按 `segmentIndex` 顺序拼接转写文本
- 拼接后文本超过 8000 字符时，返回 `transcriptTooLong` 错误
- 任一有效分段 ASR 失败时，整次流程失败，不注入部分文本
- 取消 session 时，同时取消录音和未完成的 ASR 任务

#### S19.3 ASR Provider 动态超时

作为系统，我需要所有 ASR Provider 支持按分段时长动态计算超时。

验收标准：

- 超时公式：`min(90s, max(15s, segmentDurationSeconds * 1.3 + 10s))`
- SenseVoiceASRProvider、TencentSentenceASRProvider 及其他云 Provider 统一适用
- Provider 接口支持传入分段时长参数

#### S19.4 LLM Prompt 分段转写上下文

作为系统，我需要 LLM Prompt 说明输入来自连续分段转写。

验收标准：

- 当输入来自多段分段转写时，Prompt 明确说明：输入来自同一次语音输入的连续分段转写
- Prompt 指示 LLM 按原始顺序理解为一段连续表达
- Prompt 允许合并因分段造成的断句，但禁止扩写、改写原意或补充事实

#### S19.5 分段诊断日志

作为开发者，我需要 session 级和 segment 级诊断字段，以便排查分段 ASR 问题。

验收标准：

- Session 级字段：`segment_count`、`queued_segment_count`、`max_pending_segments`、`total_recording_ms`、`joined_transcript_chars`
- Segment 级字段：`segment_index`、`segment_duration_ms`、`voiced_detected`、`forced_cut`、`silence_cut`、`asr_timeout_ms`、`asr_elapsed_ms`、`asr_result_chars`、`failure_reason`
- Debug 构建可输出完整字段；Release 构建遵守脱敏约束

#### S19.6 分段 ASR 测试覆盖

作为团队，我需要为分段 ASR 补齐测试覆盖。

验收标准：

- `AudioSegmenter` 单元测试：静音切段、强制切段、300ms 尾部保留、短录音不切段
- `SessionCoordinator` 分段编排测试：串行 ASR、结果拼接、失败中止、取消行为
- 动态超时公式验证
- 拼接文本超过 8000 字符的 `transcriptTooLong` 测试
- 分段诊断日志输出验证

### Epic 20：窗口上下文完整性与正文参考

#### S20.1 两阶段上下文采集

- 基础信息先返回，扩展正文有独立时限；失败保留基础结果。
- 绑定录音开始的应用、输入框和窗口，切换焦点不混入新正文。
- 采集可见文字最多 10000 字，选区及光标前后各 1000 字，包含清理后的网页地址及可获取的编辑能力。
- AX 读取在工作队列运行；窗口遍历有深度、节点数和时间预算。
- 字段缺失、脱敏、截断和超时状态可诊断，不记录上下文原文。

#### S20.2 内置敏感保护与 AI 参考边界

- 通用设置提供默认开启并持久化的“参考窗口上下文”开关；不提供应用/网站排除配置。关闭时新会话不采集，后续请求不发送窗口上下文。
- 密码框、认证/密钥输入、密码管理器和终端等敏感场景不发送正文、标题、标签、选区或网址；网址缺失时其他可用字段仍可提供。
- 上下文以不可信 JSON 数据提供给 polish / translate，仅辅助消歧，不得拼入未口述的已有正文。
- 重试保留原上下文来源，但在每次 AI 请求前重新检查当前开关并应用内置敏感规则，包含自动 thinking 回退；关闭后不发送任何上下文字段。
- 自动化覆盖两阶段顺序、焦点变化、超时/取消、UTF-16 边界、截断、网址清理、敏感过滤、默认采集行为及 Prompt 数据隔离。
- 真机验收覆盖原生编辑器、浏览器和 Electron 应用的字段可用性；未验收前不承诺各应用均能获取完整上下文。
