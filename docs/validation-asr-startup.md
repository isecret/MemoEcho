# 启动后实时 ASR 连接延迟排查（2026-11-07）

## 现象与范围

用户反馈：重启电脑后火山实时识别仍慢或失败，切到其他语音引擎再切回后恢复。运行版本为 beta.26。当前未稳定复现整套操作，不能宣称已确认或修复客户端根因。

## 已确认的历史证据

macOS Unified Logging 中应用 Session、ASRHotwords 与 `com.apple.network` 日志时间相互对应：

- 10:16:33.181 首包准备，连接 C8 开始。
- C8 使用代理路径，连接本地 `127.0.0.1:7890`，TCP 约 2ms 成功。
- 10:16:33.184 TLS 握手停留在 `read_server_hello`；约 2 秒后系统报告 `connect_stalled`。
- 10:16:38.185 应用取消连接，与首包发送 5 秒超时一致。
- 10:16:38.511 重试连接 C9，仍走同一本地代理；TLS 握手约 26ms 内完成，协议就绪约 228ms。
- 本次停止到文字投递 6757ms，其中 LLM 约 430ms，投递约 51ms。
- 10:17:56 使用腾讯实时，10:18:07 切回火山实时；后续火山连接就绪约 232～310ms，停止到投递约 1.2～1.7 秒。

证据证明这次失败经过代理并卡在 TLS 握手，不能据此区分代理程序、上游网络、目标服务或系统网络栈。日志中的回环 socket 是代理路径的一部分，不能仅据层级断言 TLS 的远端身份。

## 代码与对照

- 每次录音新建实时管线、URLSession 和 WebSocket，不共享上一段录音的 socket。
- 切换语音配置还会同步验证状态并可能触发合成音频验证，不能把切换效果直接解释为模型差异。
- 未携带凭据、未提交音频的 HTTPS 对照：直连三次总耗时约 3.15s、0.12s、0.14s；显式 HTTP 代理三次约 0.19s、0.14s、0.21s，均返回预期的未鉴权 HTTP 400。这只验证当前连接可达性，不等价于 WebSocket 或 ASR 验收，也不能证明历史根因。

## 本次诊断增强

- `ASRTransport` 记录随机连接 ID、握手打开事件、是否使用代理/复用连接、DNS/TCP/TLS 完成耗时、HTTP 状态、白名单错误域类别和数值错误码。
- `ASRHotwords.connection_failed` 记录随机请求 ID、失败阶段、耗时、是否超时或取消，避免取消底层连接后只有 `-999` 而丢失原始超时语义。
- 不记录 URL、主机、代理节点、请求头、凭据、系统错误正文、语音或转写内容。不更改连接路由、超时、重试次数或服务映射。
- 增加首包发送挂起后超时关闭、相同配置的新会话可继续识别的测试。这仅验证会话收尾，不模拟真实 TLS 或证明整套用户复现已解决。

验证：Debug 构建通过；`RealtimeASRProtocolTests`、`CloudASRValidationServiceTests`、`ServiceHealthMonitorTests` 共 64 个测试通过。新增首包超时测试通过；`git diff --check` 通过。测试结果不替代真实设备和网络下的复现。
