# 流式文字输出：可行性与方案草案

状态：待评审，未实施、未做微信实测。日期：2026-10-16。

## 1. 需求与结论

用户希望开启可选功能后，流式 ASR 中间结果直接出现在目标输入框；说话结束、完整 ASR 和 LLM 处理成功后，原位替换为最终结果。微信聊天输入框是重要目标。只在 HUD 显示文字、逐句粘贴后不再修改，都不满足完整需求。

结论分为三层：

- **识别端可行**：MemoEcho 已收到 ASR 中间事件，但需要统一不同厂商的文本语义并向输出层传递。
- **普通应用方案有条件可行**：仅当目标输入框提供经过验证的文本范围读写能力，才可以尝试持续替换。不能从“普通粘贴成功”推导出“流式原位替换可靠”。
- **微信场景优先验证输入法组件**：如果其输入框不提供可靠的 AX 文本范围，普通应用无法依靠现有接口可靠管理已写入的片段。输入法组合文字机制更符合需求，但尚未验证当前微信版本的长时间组合文字、异步更新及最终提交。

不是所有实时显示都必须成为系统输入法；但要覆盖微信这类输入框，并接近中文输入法的组合、修改、提交体验，建议评估一个可选的 macOS 输入法组件。此组件可以只负责语音文字输出，不要求实现拼音词库或候选词引擎。

这仍然是新增系统输入源与输入法进程，属于现有“菜单栏助手，不是系统输入法”范围的扩展。本草案不代表已经批准架构变更。

## 2. 为什么 AX 和输入法是两条路线

| 路线 | 目标应用中的文字 | 最终替换方式 | 适用边界 |
| --- | --- | --- | --- |
| HUD 预览、结束后粘贴 | 结束前没有文字 | 沿用一次定向粘贴 | 改动较小，但不满足直接在输入框展示的要求 |
| AX 局部修改 | 已写入的普通正文 | 验证原有片段和范围后再修改 | 依赖每个输入控件的读写能力，不能覆盖未提供范围的微信输入框 |
| 输入法组合文字 | 当前输入会话管理的 marked text | 更新组合文字；最终通过输入法提交 | 符合需求语义，仍需测试目标应用与会话中断行为 |

AX 是辅助功能接口；输入法通过文本输入协议与编辑控件协作。**非标准 AX 输入框，不等于不支持输入法组合文字。** 微信能够进行中文输入，支持了验证输入法路线的方向，但这不能替代本功能的实测。

Apple 的 `updateComposition()` 会把组合文字通过 `setMarkedText` 发给客户端；`commitComposition` 表示客户端要求结束当前组合会话。因此输入法也不能无限持有、修改一段已经提交的正文。[Apple InputMethodKit](https://developer.apple.com/documentation/inputmethodkit/imkinputcontroller/updatecomposition())；对应行为也已核对本机 Xcode SDK 的 `IMKInputController.h`。

AX 属性是否可写必须逐元素查询。设置选区、写文字、读回是多次调用，不能视为跨进程的原子替换；检查后仍可能遇到用户操作或目标应用变化。[Apple AXUIElementIsAttributeSettable](https://developer.apple.com/documentation/applicationservices/1459972-axuielementisattributesettable)

不建议把以下做法作为微信的正式方案：按字符数退格后重打、全选后覆盖整框、频繁占用剪贴板、模拟撤销。这些办法无法可靠区分 MemoEcho 文字、用户修改、表情和已经发送的消息。

## 3. 同类证据与证据限度

- **soink**：官方页面描述在输入位置实时显示语音文字；更新记录明确出现输入法就绪检测、快捷键切换输入法，以及组合文字提交相关修复。说明同类产品确实有采用输入法集成的路线。未安装实测，也未验证其微信兼容性或私有实现。[官网](https://www.soink.ai/) / [更新记录](https://www.soink.ai/changelog)
- **Purr**：项目介绍中的 Smart Typing 不能直接当作相同功能的证据。检查固定版本源码后，其 `runStreamingTask` 明确将 partial 用于 HUD，停顿形成完整句子后处理并粘贴，已经提交的文字不再重写。这与“整次录音结束后原位替换为 LLM 结果”不同。[源码，固定提交](https://github.com/iamarunbrahma/purr/blob/fd929a640b77b8a253324b25393eb488609f5d0f/Sources/Purr/AppCoordinator.swift#L745)
- 未核实微信输入法的内部实现；不据其表面效果推断私有接口或实现细节。

目前属于代码与接口层面的可行性评估，不能称为微信兼容性验收通过。

## 4. 推荐的条件方案

### 4.1 用户操作

设置 → 文字处理，新增“实时显示识别文字”，默认关闭。配置缺省值为 `false`，旧配置正常加载；本次录音采用开始时的配置快照。

开启需要安装并启用可选输入法组件。首次引导应明确系统输入源的变化；不能只放一个开关，却隐藏安装和切换要求。输入源自动切换、恢复原输入源是否可靠，需要在验证阶段确认。

正常流程：

1. 开始录音，建立目标客户端对应的组合会话。
2. ASR 返回中间结果，持续更新同一段组合文字；识别纠正时替换已有草稿，不追加重复内容。
3. 松开或再次按快捷键结束录音，等待 ASR 明确 final，继续在原位保留草稿。
4. 将完整 final 交给 LLM；翻译模式仍为 polish → translate。
5. 仅在原组合会话仍有效时，用最终文本结束组合并提交一次。

示例：`明天三点开` → `明天下午三点开会` → LLM 完成后提交 `明天下午三点开会。`。示例仅表示交互过程，不承诺具体模型输出。

只对已验证能产生中间文字的服务生效。SenseVoice、OpenAI Audio Transcriptions、MiMo 和 HTTP 分段入口继续现有流程；WebSocket 入口也不能仅凭协议类型就认定支持实时预览。该功能不会消除麦克风启动等待或 ASR 首包延迟。

### 4.2 会话边界

| 情况 | 建议行为 |
| --- | --- |
| 目标控件不支持组合文字，且尚未写入草稿 | 提示本次使用完成后输出；沿用现有最终粘贴流程，不切换 ASR 服务 |
| 用户切换窗口、点选其他位置、切换输入法，或目标客户端要求提交 | 结束该组合会话的自动管理；后续 LLM 结果不再覆盖原位置，也不追加到新位置 |
| 会话已结束，但随后得到有效 LLM 结果 | 进入明确的输出中断状态，通过菜单提供手动“复制结果”，不自动复制 |
| LLM / ASR 失败，组合会话仍由我们持有 | 建议撤销本次组合文字并报错，延续失败不提交的产品原则；原有选中文字的恢复要单独验收 |
| 失败前目标应用已经强制提交草稿 | 不删除已提交正文；提示草稿可能已经保留，禁止迟到结果继续修改 |
| 用户取消 | 取消音频和处理任务；仍有效的组合会话撤销，已经提交或失去控制的正文不自动删除 |
| 用户按 Enter | 需验证与微信“确认组合文字 / 发送消息”的配合，不能由异步结果触发发送；不默认吞掉用户的发送操作 |

“等待 LLM 期间仍在组合状态”不意味着永久保有替换权。用户操作或目标应用可能结束组合；此时必须放弃自动替换。输入法组合文字也不能被视为目标应用完全不可见的数据，不能承诺其绝不被应用保存或处理。

## 5. 对 MemoEcho 的改动

| 模块 | 现状 | 拟议改动 |
| --- | --- | --- |
| ASR 适配器 | `partial(text:)`、`stableSentence`；厂商增量与纠正语义不同 | 在适配器内生成带窗口标识、递增版本的完整预览快照，处理撤回、纠正、重复事件 |
| `RealtimeRecognitionPipeline` | 消费 partial 仅记录首包耗时；多窗口后台接续 | 按音频窗口顺序汇总预览，隔离预连接、旧窗口和迟到事件；final 仍是进入 LLM 的唯一依据 |
| 预览输出通道 | 不存在 | 只保留最新快照，串行、限频输出；不能阻塞音频发送或 final 收尾 |
| `SessionCoordinator` | final → LLM → 一次粘贴 | 管理组合会话身份、生命周期及最终提交；取消或失活后拒绝迟到写入 |
| 可选输入法组件 | 不存在 | 通过 InputMethodKit 管理 marked text；通过受限本地 IPC 接收当前会话的快照与最终结果 |
| `TextInjector` | 一次定向粘贴、约 500ms 后恢复剪贴板 | 保留关闭功能及开始前判定不支持时的路径；不可用于已写入草稿后的自动追加兜底 |
| 配置、设置、恢复 | 无此开关及输出中断语义 | 向后兼容解码；区分无草稿、组合中、已提交、失活，恢复处理不重写已失去控制的内容 |

建议预览更新从 100–200ms 的合并间隔开始实测，属于待验证参数，不是性能承诺。UTF-16 范围与中文、emoji、组合字符必须一致；最终文本 8000 字符上限、单 active session 和取消要求继续保留。

窗口上下文在首次草稿写入之前捕获，不能让自己的实时草稿再次成为上下文。任何额外的范围校验读取只在本地使用，不得绕过“参考窗口上下文”的上传开关。正式结果完成前不进入纠错学习流程。

输入法组件与主应用只传递当前会话所需内容，校验通信对端；音频仍由主应用处理，不新增音频或文本历史。进程退出、断连、切换输入源时失效旧会话。安装、升级、卸载、CI 签名和公证需要覆盖新增组件，不采用临时本地签名作为交付方案。

## 6. 先做什么验证，什么情况下才继续

先验证**微信输入框的组合文字能力**，通过后再接入 ASR / LLM。验证使用固定的合成文字模拟 partial 与 final，无需录音、访问真实聊天内容或发出消息。

1. 在经用户选择的微信测试输入框内建立组合会话：连续更新、中文纠正、emoji、多行，最终替换和一次提交。
2. 模拟 ASR 完成后 LLM 延迟 1 / 3 / 10 秒，检查等待期间组合是否保持、控件是否强制提交。
3. 验证点光标、手动打字、Enter、Esc、换聊天、换窗口、切换输入法：失活后迟到结果不得写入其他位置或发送消息。
4. 验证原有选中文字、前后已有正文、输入法取消、主应用退出和 IPC 断开，记录是否存在丢字、重复、错误替换。
5. 验证长录音对应的持续组合与接近 8000 字符的文本规模；记录目标应用版本和不支持的行为，不能用短句成功替代长文本验收。
6. 微信通过后，再验证原生文本框、浏览器 textarea、Electron 编辑器等。兼容性逐项记录，不宣称“所有输入框可用”。

**继续条件**：微信目标版本能稳定保持并更新组合文字，正常结束能提交一次，中断后不会继续写入，且不需要盲删、全框覆盖或私有接口。否则暂停这条实现路线，保留 HUD 预览作为不同体验的备选，由用户决定是否接受。

验证通过后再同步 PRD、TDD 和任务拆分，实施预览语义归一化、输入法组件、设置及恢复流程。单元测试覆盖乱序 / 重复 partial、ASR 窗口切换、取消后的迟到事件、失败、配置兼容与已失活会话禁止提交；跨应用交互必须手工验收。

## 7. 评审前需要明确的范围

- 用户是否接受安装并启用一个可选的“MemoEcho 语音输入法”组件；仅菜单栏应用与此方案不是同一开发范围。
- 输入框内先出现识别草稿，意味着不能再无条件声称“LLM 成功前目标应用绝无文字”。
- 目标应用提前结束组合后，接受停止自动替换、改为手动取回最终结果。

本轮仅形成方案和可行性判断；未改动 PRD / TDD 的现行约束，未实现功能，未构建或发布版本。
